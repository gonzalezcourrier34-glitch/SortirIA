Le mode d'emploi

Construire SortirIA ne suffit pas : il faut savoir l'exploiter. Cette page rassemble les gestes que je fais, ou que ferait quelqu'un qui reprendrait le service : installer le poste, lancer une collecte, trancher les propositions de l'agent, brancher une source ou un partenaire, mesurer, déployer, revenir en arrière, réagir à un incident. Pour chaque procédure : la commande exacte (PowerShell et uv, sous Windows), ce qu'on doit voir, et quoi faire si ça échoue. Chaque option a été relevée dans le code (argparse des modules), aucune n'est inventée.

PROCÉDURE 3.1 · APRÈS CHAQUE MAIL QUI EN ANNONCE

GitHub
BUT

UNE FOIS

Un jeton GitHub « fine-grained » limité au dépôt SortirIA (droits Contents et Pull requests en écriture), rangé en secret de la tâche sortiria-collecte (GITHUB_TOKEN_AGENT). Sans jeton, pas de PR : on décide en ligne de commande, ci-dessous.

SI ÇA ÉCHOUE

PR en conflit (le fichier a changé entre-temps) : l'agent la refait sur main à jour la nuit suivante. Proposition qui ne peut pas devenir une PR (document absent du dépôt, adresse présente deux fois) : le mail le dit, elle se décide à la main.

Sécurité au quotidien

Aucun secret dans le code, l'image ou la documentation. Les clés vivent à trois endroits, et chacun a sa façon d'être mis à jour.

Sur le poste

.env (développement) et .env.azure (adresse de la base de production et mots de passe). Les deux sont exclus de git (.env.* sauf .env.example) et de l'image Docker (.dockerignore).

Sur Azure

Les secrets Container Apps de l'API et de la collecte : chaque variable du .env devient un secret (nom en minuscules, _ remplacé par -, par exemple mistral-api-key), lu par secretref:. Le jeton d'envoi de Static Web Apps est lu dans Azure à chaque déploiement, et masqué.

Sur GitHub

AZURE_CLIENT_ID, AZURE_TENANT_ID, AZURE_SUBSCRIPTION_ID : des identifiants, pas des mots de passe. La connexion se fait par OpenID Connect, limitée à la branche main et au seul groupe sortiria-rg ; rien à renouveler. La variable DEPLOY_ENABLED active le déploiement.

PROCÉDURE 9.2 · CLÉ COMPROMISE OU RENOUVELÉE

Changer une clé

API et collecte
BUT

Remplacer une clé (Mistral, OpenAgenda, DATAtourisme, SMTP) partout où elle sert, sans qu'elle s'affiche ni reste dans un fichier suivi. L'API et la tâche de collecte ont chacune leurs secrets : il faut mettre à jour les deux.

ORDRE

Créer la nouvelle clé chez le fournisseur ; la mettre dans .env et .env.azure ; mettre à jour les secrets Azure ; redémarrer la révision de l'API ; vérifier ; révoquer l'ancienne en dernier.

PowerShellexemple : la clé Mistral ; aucune valeur écrite dans la commande
$cle = Read-Host "Nouvelle clé Mistral"

# Secrets de l'API et de la tâche de collecte
az containerapp secret set --name sortiria-api --resource-group sortiria-rg --secrets "mistral-api-key=$cle" --query "[].name" -o tsv
az containerapp job secret set --name sortiria-collecte --resource-group sortiria-rg --secrets "mistral-api-key=$cle" --query "[].name" -o tsv
Remove-Variable cle

# L'API ne relit ses secrets qu'au redémarrage de sa révision
$REV = az containerapp revision list --name sortiria-api --resource-group sortiria-rg --query "[?properties.active].name | [0]" -o tsv
az containerapp revision restart --name sortiria-api --resource-group sortiria-rg --revision $REV

# Vérifier : en local, puis en production
uv run python -m scripts.check_mistral
Invoke-RestMethod https://www.sortiria-montpellier.fr/api/v1/sources
CE QU'ON DOIT VOIR

Les noms des secrets (pas leurs valeurs), « HTTP 200 » trois fois pour check_mistral, une réponse du site. La collecte prendra la nouvelle clé à sa prochaine exécution.

SI ÇA ÉCHOUE

HTTP 401 après le changement : l'ancienne clé a été révoquée trop tôt ou la nouvelle est mal recopiée. Ces commandes secret set et revision restart sont standard dans Azure CLI mais n'ont pas encore servi sur ce projet : en cas de doute, az containerapp secret set --help donne la syntaxe de la version installée.
