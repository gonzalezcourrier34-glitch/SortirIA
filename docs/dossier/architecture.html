SORTIRIA · ARCHITECTURE

Deux chaînes,une base

J'ai construit SortirIA comme deux chaînes qui partagent une seule base PostgreSQL : la nuit, un agent LangGraph collecte, vérifie et enrichit les événements ; le jour, une API répond aux questions en cherchant dans cette base, puis Mistral rédige une réponse qui ne cite que des événements réels.

01

Vue d'ensemble

Le schéma ci-dessous est le plan de tout le projet. À gauche, ce qui tourne chaque nuit ; à droite, ce qui répond au visiteur ; au milieu, la base qui les relie.

La collecte prépare tout ce qui coûte du temps ; la recherche n'a plus qu'à filtrer, classer et rédiger.

J'ai séparé les deux chaînes parce qu'elles n'ont pas le même rythme. La nuit, l'agent a le temps : il lit les sources, écarte ce qui n'est pas une sortie, fusionne les doublons entre sources, fait enrichir chaque nouvel événement par Mistral (catégorie, publics, résumé), calcule son vecteur, puis fait juger 20 fiches par un autre modèle.

Le jour, il faut répondre vite. L'API comprend la question par des règles (sans appel à un modèle), applique des filtres SQL stricts, cherche par le sens et par les mots dans la même base, puis Mistral rédige 2 à 4 phrases. Une boucle relie les deux : chaque lundi, ce que les visiteurs ont cherché sans trouver revient à l'agent, qui propose de quoi y répondre.

Sept nœuds LangGraph, un état partagé et des décisions : réessayer une source, ne pas vider la base quand une API tombe, alerter sur une baisse, proposer une réparation sans l'appliquer.

Les données

Un seul schéma sortiria : 13 tables et 6 vues, écrits pour SortirIA les 13 et 14/10/2026 puis complétés. Trois lecteurs s'en servent : l'agent qui l'écrit chaque nuit, la recherche qui lit une vue, et Grafana qui lit les tables de suivi.

La table centrale : events

Une ligne par séance, quelle que soit la source. Son identifiant est une empreinte du titre, du jour, de l'heure et du lieu normalisés : deux sources qui annoncent le même concert produisent la même ligne, ce qui rend la mise à jour de chaque nuit possible. Le vecteur de 1 024 dimensions est dans la même table, avec un index HNSW : un filtre SQL et une distance cosinus tiennent dans une seule requête.

Les vues, seule porte de lecture

Personne ne lit events directement. La recherche lit v_upcoming_events, qui porte les règles : source active, ni annulé, ni reporté, ni uniquement en ligne, pas passé, début dans les 3 mois ; « maintenant » y est lu dans sortiria.reference_now(), que la base de test fige sur l'instant de son export. Changer une règle se fait donc en un seul endroit.

Les règles que la base garantit

  • un événement mis en avant a forcément un partenaire ;
  • la fin ne précède pas le début, l'âge minimal ne dépasse pas l'âge maximal ;
  • un avis vaut −1 ou 1, une seule fois par proposition ;
  • les vocabulaires (statut, publics, motifs) sont fermés par des contraintes CHECK.

Ce qui vit combien de temps

  • événement passé : 7 jours (pour pouvoir le noter), jamais proposé ;
  • questions et avis : 90 jours ; cache : 1 jour ; collectes : 1 an ;
  • plafond de 10 000 événements, les plus lointains partent d'abord ;
  • une suppression laisse une statistique, jamais la fiche.
À RETENIR Ces règles sont des contraintes PostgreSQL : même un bug dans le code ne peut pas les contourner.

Le schéma est vérifié sur un vrai PostgreSQL par tests/event/test_schema_postgres.py (contraintes, vues, suppressions avec statistiques, fenêtre de notation, requêtes des tableaux Grafana), en local comme dans la CI.

04

Le chemin d'une question

Une question traverse l'API en quatre étapes visibles (comprendre, rechercher, filtrer, rédiger), diffusées une à une à l'interface, puis laisse une ligne dans le journal.

01 • Garde-fous

Limite de débit et cache

12 recherches par minute et par visiteur, 1 000 par heure pour tout le service (réponse 429 au-delà). Une même demande, le même jour, sur la même collecte, est servie sans appel à Mistral.

02 • Comprendre

Des règles, pas un modèle

app/query_understanding.py lit quand, où, pour qui, gratuit ou budget, intérieur ou plein air, le type de sortie et les mots-clés ; les cases cochées s'y ajoutent, une relance (« et pour les enfants ? ») complète la question précédente.

03 • Rechercher et filtrer

SQL strict, puis le sens et les mots

Filtres SQL (période, lieu, public, budget, cadre), puis recherche par le sens (pgvector) et par les mots (plein texte français), fusionnées par rang. Si rien ne parle du sujet, il est cherché en relâchant les contraintes, et la réponse dit ce qui diffère.

04 • Rédiger

Une réponse sourcée

Mistral ne reçoit que les événements trouvés, numérotés ; une citation qui ne renvoie à aucun d'eux est retirée. Sans Mistral, une réponse simple liste les événements, signalée à l'écran. La recherche en détail →

Limite de débit

Les routes de l'interface sont ouvertes sans clé : sans limite, un script pourrait poser des milliers de questions payées à Mistral. app/rate_limit.py limite chaque visiteur et plafonne la recherche pour tout le service, même si un robot change d'adresse à chaque question.

Secrets hors de git

Les clés et l'adresse de la base vivent dans un .env local ignoré par git et dans les secrets d'Azure ; .dockerignore exclut .env et les notes personnelles de l'image, qui tourne sans droits d'administrateur.

Déploiement sans mot de passe

GitHub se connecte à Azure par OpenID Connect : Azure fait confiance à ce dépôt et à sa branche main, avec des droits limités au groupe de ressources sortiria-rg. Le déploiement →

Le modèle sous contrôle

Liste fermée de catégories, résumé écarté s'il cite un nom ou un nombre absent de la source, citations vérifiées, commentaires modérés par Mistral Moderation, juge de qualité chaque nuit.
